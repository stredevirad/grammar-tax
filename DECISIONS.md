## Phase 1: harness

- **D1.1 What is timed.** The replay tool calls the internal API `llama_grammar_apply_impl` (full mask over the whole vocab) and `llama_grammar_accept_impl` per recorded token. This is exactly what `llama_sampler_grammar_apply/accept` call, minus a pointer hop. The internal API is used (header `src/llama-grammar.h`, like the upstream tests do) so the tool can also read the number of live stacks.
- **D1.2 Full mask every step is the worst case, not the common case.** `common_sampler_sample` first samples without the grammar and only checks the one chosen token (cheap); the full-vocab mask runs only when that token is rejected (or when `grammar_first` is set). So the replay measures the cost of the slow path. Real end-to-end cost per token = (fraction of steps that need the full mask) x (mask cost) + (single-token check). Reported this way in baseline.md. The trace recorder applies the full mask every step (grammar first) so traces are always grammar-valid.
- **D1.3 Recording settings.** Chat template from the GGUF, system prompt "answer only in requested format", top-k 40, temp 0.7, seeded dist (seed 1234), max 256 generated tokens, 120 s wall cap per grammar. Truncated traces are fine: replay only needs a valid prefix. Recorded with 2 parallel jobs x 2 threads (grammar is single threaded). Trace files record the metadata line (model, seed, n_prompt, n_gen, complete, timings).
- **D1.4 Schema sample.** JSONSchemaBench HF dataset `epfl-dlab/JSONSchemaBench` at revision `5bd0f46`, test split of the 10 subsets (Github_trivial/easy/medium/hard/ultra, Glaiveai2K, JsonSchemaStore, Kubernetes, Snowplow, WashingtonPost), 20 per subset with pandas `sample(random_state=42)` = 200 schemas. Prompt includes the schema (pretty-printed, truncated to 6000 chars).
- **D1.5 Conversion** uses llama.cpp's C++ `json_schema_to_grammar(common_json)` (same entry point as `--json-schema` and the server), via `bench/schema_to_gbnf`. All 200 sampled schemas converted (0 failures; `data/conversion_failures.tsv` is empty apart from the header). The converter is tolerant: unsupported keywords are dropped with warnings rather than failing.
- **D1.6 Mask hash.** FNV-1a 64 over the per-token reject byte (logit == -inf) in vocab order, one hash per step, plus `n_allowed`. Two builds agree bit-for-bit iff every line of the `--check` file matches.
- **D1.7 Callgrind build.** valgrind 3.22 aborts on AVX-512 (EVEX) instructions emitted in ggml-cpu by `-march=native`. Profiling uses a second build `build/cg-base` with `-DGGML_NATIVE=OFF` (ggml-cpu gets AVX2/FMA only). libllama (where all grammar code lives) is compiled with plain `-O3`, no `-march`, in both builds, so the profiled grammar code is the same machine code family as the timed one. Collection is restricted with `--toggle-collect` to `llama_grammar_apply_impl` and `llama_grammar_accept_impl` so vocab loading is excluded.
- **D1.8 Background job limit.** The first recording job was stopped by the 30 min background limit after 146/208 grammars; the recorder writes a trace only when a generation finishes, and the script skips existing traces, so the rerun only re-did the 2 in-flight grammars. No partial traces exist.
- **D1.9 End-to-end subset.** `data/e2e_subset.txt` = all 8 built-in gbnf + the first 2 (by sorted id) of each JSONSchemaBench subset = 28 grammars. Each runs twice with the real model (4 threads, one job): `--mode first` (full mask every step) and `--mode resample` (mirror of `common_sampler_sample`). This measures how often the full mask is actually needed on the default path, which matters because upstream PR #6811 (codepoint cache) was closed in 2024 after the resampling fix (#7424) made the full mask rare end to end.
- **D1.10 Workload-level metrics.** "Median per-token grammar cost" = median over grammars of each grammar's mean (mask + accept) time per token. "p99" = 99th percentile over all replayed tokens pooled. Both are computed per run; reported as median over runs with [min .. max] and the run count.
- **D1.11 Duplicate ids in JSONSchemaBench.** The JsonSchemaStore test split has 7 duplicate `unique_id`s; our seeded sample drew three different schemas all named `project-1`. They mapped to the same file names, so the last one written won and the manifest had 3 identical rows. Fixed by keeping one row per name (prepare_workload.py and analyze.py both de-duplicate). The workload is therefore **206 distinct grammars**: 8 built-in .gbnf + 198 schemas (JsonSchemaStore contributes 18, every other subset 20). The baseline run that was already in flight replayed `project-1` three times; analysis drops the duplicate rows.

- **D1.12 llguidance reference.** Built with `-DLLAMA_LLGUIDANCE=ON` in 127 s (under the 10 min budget). `llama_sampler_init_llg` returns a sampler with a null matcher when llguidance rejects a schema, and that sampler masks nothing; `llg_replay` therefore marks a schema `unsupported` if the first mask rejects zero tokens (36/198). A schema is `diverged` if llguidance forbids a recorded token (39/198); its timing covers the prefix before that point. llguidance runs with its defaults (no `coerce_one_of`).
- **D1.13 Capped callgrind.** Full worst-10 traces under callgrind would take 3+ hours (~50x slowdown). Callgrind runs use `grammar_replay --max-steps 40` (first 40 tokens of each trace); perf cpu-clock sampling covers the full traces on the native build. The cap biases toward early-trace behavior; both views are reported.
- **D1.14 TinyLlama pass.** Recorded with 2 jobs x 1 thread while callgrind ran, paused (killed; recorder writes traces only on completion, so no partial traces) to keep the e2e runs on a quiet machine, then resumed with 2 x 2 threads. Replayed 3 runs (not 5): it is a secondary vocab-size data point and each run is only ~2.3 min, spread was 3%.
- **D2.1 Gate metric vs end-to-end.** The GATE is evaluated on the replay metric the brief defines (full mask per token). The end-to-end measurement (5.1% of default-path steps need the full mask) is reported next to it in profile.md, with projections for both the default path and the full-mask-every-step path, so the limited default-path benefit is not hidden.

## Phase 3: optimize

- **D3.1 One worktree per variant.** `build/src-patched` = 0001 only (frozen), `build/src-p2` = 0001+0002, later variants get their own `build/src-<name>`; each has its own build tree `build/bench-<name>` (and `build/cg-<name>` for callgrind). This keeps each build tree consistent with its source; a rebuild never silently picks up a later patch.
- **D3.2 Patch files without commits.** `scripts/make_patch.sh` writes git format-patch layout files from worktree diffs (against the pinned SHA, or against the previous variant's worktree for stacked patches). No commit objects are created in the submodule repository. `scripts/apply_patches.sh` applies the series with `git apply --check` first; every generated patch was re-applied to a fresh worktree and compared byte-for-byte with its source tree.
- **D3.3 Patch stacking.** 0002 applies on top of 0001 (both edit the end of `llama_grammar_apply_impl`); they are separate ideas and are measured separately (base -> p1 -> p2).
- **D3.4 P2 placement.** `test-llama-grammar` asserts the exact order of the reject list returned by `llama_grammar_reject_candidates_for_stack` (tests/test-llama-grammar.cpp:375-393), so P2 leaves that function and `llama_grammar_reject_candidates` untouched and only changes the top level in `llama_grammar_apply_impl`, which uses the reject set, not its order.
- **D3.5 Correctness gates for every patch:** (1) the 4 grammar tests; (2) `scripts/check_masks.sh`: bit-exact per-step mask hashes vs baseline on all 206 traces for both vocabs (23,448 + 21,202 steps); (3) `scripts/run_fuzz.sh`: random valid walks through all 8 `grammars/*.gbnf` + 7 edge-case grammars in `bench/fuzz_grammars/` with both vocabs (13,499 + 3,668 steps), compared line by line with baseline. Coverage counters (results/fuzz/base/*.cov.jsonl) confirm the walks hit partial UTF-8 carried into a step, byte-fallback single-byte tokens, multibyte tokens, EOG allowed and taken, empty stacks, char ranges, alternates, negated classes, any-char, TOKEN and TOKEN_NOT tops.
- **D3.6 Who benefits (audit).** results/who_benefits.md. Correction to Phase 2: the speculative drafters in `common/speculative.cpp` (used by llama-server) build samplers without the grammar, so `grammar_first = true` there costs nothing; only the `llama-speculative` example (both samplers from `params.sampling`) and applications that put the grammar sampler in a `llama_sampler` chain pay the full mask every step.
- **D3.7 Stack-count wording (baseline.md).** "Stack count only matters above ~100" came from the per-grammar mean-vs-peak scatter and was wrong as a statement about cost; per-step medians show ~2.3 ms per live stack from 1 to 556 stacks (16 ms + 2.3 ms x stacks within ~5%), plus up to ~2x when most of the vocab passes the first char. baseline.md and profile.md corrected; new chart `step_cost_vs_stacks.png`.
- **D3.8 Unexplained rc=1 in the first P1 mask check.** The first `check_masks.sh base p1` run printed MASKS IDENTICAL for both vocabs (all 23,448 + 21,202 steps present) but exited 1, and the old script deleted the shard stderr files. Investigated: a full sharded Qwen baseline replay with per-shard exit codes (all 0, no `ok:false` rows), the P1 TinyLlama shards (all 0), and a rerun of the TinyLlama check (exit 0). Not reproduced; the mask files are complete in all cases, so the comparison stands. The script now keeps stderr and names any process that exits nonzero; the P2 check exited 0. **Explained later (final polish, 2026-10-17):** a glob bug in `check_masks.sh`. The second build's loop expanded `shard.$TAG.*` after the first build had written `shard.$TAG.NN.<a>.masks` / `.err` next to the shard manifests, so the second build also ran on those 8 files as if they were manifests; every line failed "cannot read trace" (exit 3), and that stderr went to files outside the `??` glob that was collected. The real 4 shards and the mask comparison (which reads only `shard.$TAG.??.*`) were unaffected, so every MASKS IDENTICAL verdict stands. It only showed when the first build's masks were not cached, which is why reruns exited 0. Fixed by listing the shards right after `split`; found when `scripts/quick_verify.sh` (always uncached) hit it.
- **D3.9 #28371 third arm.** Fetched read-only (`git fetch origin pull/28371/head`, head `f000de6`, 6 commits on `4cbe8b0`). Its net diff (src/llama-grammar.cpp +63/-5, src/llama-grammar.h +66) applies cleanly to the pinned SHA (`patches/third_party/pr28371-f000de6.diff`), ~1 min into the 15 min budget. - **D3.10 apply_patches.sh footgun.** With no patch arguments it applies the whole series; `none` now means a pristine worktree. (This briefly made the first #28371 apply check run against 0001+0002; redone on a pristine tree.)
- **D3.11 #28371 head (f000de6) fails the correctness gate.** On our workload its masks differ from baseline (first difference: `gbnf__english`, Qwen trace, step 56) and it segfaults in the random-walk test (Qwen vocab) and in the combined arm's replay (`japanese.gbnf`). Cause, confirmed with valgrind memcheck (TinyLlama vocab, english.gbnf, 12 steps): 8,829 errors, all "Invalid read of size 4" in `llama_grammar_candidates_hash::operator()`; baseline on the same run: 0 errors. *(Corrected 2026-10-17: the 8,829 errors come from 30 contexts of three kinds, 12 "Invalid read of size 4", 14 "Conditional jump or move depends on uninitialised value(s)", 4 "Use of uninitialised value of size 8"; 2 contexts have `llama_grammar_candidates_hash::operator()` as top frame, the rest the hash table's find/rehash for the same cache. Logs in `results/pr28371/`.)* The memo cache key (`memo_cache[stack][candidates]`) stores a copy of the candidate vector, whose `code_points` members are raw pointers into the per-call decode buffers that `llama_grammar_apply_impl` frees on return. Since commit f000de6 ("preserve grammar memo cache between steps") the cache is no longer cleared per call, so later steps hash and compare keys through freed memory: wrong cache hits (wrong masks) or crashes. The PR's previous commit c29085b clears the cache at the start of every apply ("cache keys hold raw pointers into candidates_decoded; clear before rebuilding"), which avoids this. **Decision:** measure c29085b as the #28371 arm (`bench-pr28371c`; combined with ours: `bench-comboc`, `patches/third_party/pr28371-c29085b-on-0002.diff`), and report f000de6 as failing the gate with this evidence. Read-only: nothing was posted upstream; whether to tell the PR author is the user's call.
- **D3.12 VM reboot mid-study (kernel change).** During run 3 of the small-ideas A/B (`results/raw/ab-small`) the session worker and the VM restarted (uptime 0), and the guest kernel string changed from `6.18.44-fc-v114` to `6.18.44-fc-v139`. Disk, builds and models were intact; all background jobs died. Runs 1-2 of `ab-small` were complete for all five arms (p1, p1skip, p1eog, p1ascii, p2b) and are the record (`results/ab-small/`); the partial run 3 (p1, p1skip only) is kept under `results/raw/ab-small/partial-run3/` and not used. Every A/B before this point ran on fc-v114; later ones record `kernel=` in their meta.txt.
- **D3.13 Page-fault pathology: a cold-start allocator effect (corrected).** First seen after the reboot: replaying the 600-stack grammar o46322 *alone*, P1 was much slower than baseline. A first explanation (the kernel changed) was wrong; the direct test is process history. o46322 alone in a fresh process vs o46322 after one other grammar (gbnf json) in the same process, fc-v139: **base 282.8 ms (3.4M page faults) vs 227.2 ms (87k); P1 415.9 ms (20.9M faults) vs 196.3 ms (44k)**. Mechanism: `llama_grammar_reject_candidates_for_stack` reserves two vectors of `candidates.size()` (~4.8 MB at the top level) per call, i.e. per live stack per step. glibc serves allocations above its mmap threshold (128 KB at process start, raised dynamically after large frees) with mmap, so until the threshold has adapted every such reserve is an mmap + ~1,200 page faults + munmap. In the baseline the ~152k small per-token vectors live in the heap during the sweep, which changes what glibc does with the big blocks; P1 removes them, so a cold process pays the full mmap/fault cycle per stack. perf on the cold P1 run: ~25% of time in kernel fault handling (do_user_addr_fault, memcg1_commit_charge, clear_page_erms). The pre-reboot "loaded machine" smoke test of o46322 alone (P1 ~390 ms) was the same cold start. In the A/B workload runs the stack-heavy grammars never run first in a process (manifest order: built-in grammars first), so the A/B numbers are the warm case. P2b passes each stack only the small matching subset, so it does not make the big per-stack allocations in either case (cold o46322: 0.23M faults).
- **D3.14 A misleading smoke test.** A single replay of o46322 run while correctness checks loaded the machine showed P2b at ~half of P1 (180 vs 390 ms). On the quiet pre-reboot kernel the A/B showed no such gain (P1 162.8, P2b 169.8 ms). The smoke test measured P1's fault/contention slow mode, not P2b's scan. Only interleaved A/B runs on a quiet machine are used for decisions.
- **D3.15 Cold-start regression confirmed end to end, and fixed with 0003.** Cold A/B (each of the median-9 + worst-10 grammars replayed alone in a fresh process, 2 rounds, `results/raw/cold-final`): 0001+0002 vs base 1.250x per grammar, but o46322 0.625x (234.5 -> 375.5 ms/token), rustfmt 0.756x, sp_408 0.806x. End to end with the real model in a fresh `grammar_record` process (full mask every step): o46322 grammar time 53.1/51.6 s (base) vs 81.0/82.7 s (0001+0002), rustfmt 22.1/21.5 vs 30.7/32.1 s. Confirmed as glibc mmap/trim behavior: with `GLIBC_TUNABLES=glibc.malloc.mmap_threshold=67108864:glibc.malloc.trim_threshold=268435456`, cold o46322 is base 213.2 ms (26k faults) vs 0001+0002 162.5 ms (18k faults). Fix: patch 0003 reuses two reject lists across stacks in `llama_grammar_reject_candidates` via an internal `..._for_stack_into` variant; public `llama_grammar_reject_candidates_for_stack` unchanged (wrapper). Cold o46322 with 0001+0002+0003: 180.3 ms, 0.6M faults. Passes all gates. Timing (cold A/B, e2e cold, 5-run warm A/B, e2e, llama-bench, TinyLlama) queued in `build/queue-final.sh`.
